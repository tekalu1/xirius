# コマンドの接続と結果

引数とコマンドの一覧は、コマンド表から生成する [commands.md](commands.md)。
CLI の直接実行は標準出力の JSON と終了コードを返す。`request_key`・`wait_ms` は MCP の制御欄。

## 版の照合

コマンドのプロトコルは v1。MCP の initialize の `_meta.xirius.command_protocol` と、サーバーが返す同じ欄を照合する。指定が無い従来のクライアントは v1 として照合する。異なる版番号と、数値でない指定は接続時に拒否する。
`ops.hello --version 1` でも照合できる。

## 受領証と再送

MCP の編集には `receipt` が付く。`completed` は処理が終了した状態であり、成功か失敗かは `ok` と `error.code` で確かめる。

| state | 意味 |
|---|---|
| accepted | 受け付けた。ユーザーの承認待ちもこの状態 |
| running | 実行中。長い処理のジョブ ID が付くことがある |
| completed | 結果が確定した。失敗や中断も型付きの結果を返す |
| unknown | 待ち時間切れなどで結果を確認できない。実行が続いている可能性がある |

同じ MCP サーバーの存続中は、再送に同じ `request_key` を付ける。同じキーで同じ操作を送っても再実行しない。引数のオブジェクトの並びは問わない。同じキーで引数やコマンドを変えた場合は `conflict`。
`wait_ms: 0` は受付後にすぐ返す。長い処理は MCP では常にバックグラウンドで実行し、既定の待ち時間は 0。通常の編集では、省略時に最初の結果を最大 30 秒待つ。タイムアウトから完了しても、受領証の ID は変わらない。

受領証の保存上限は 4,096 件、操作の指紋の合計は 64 MiB。上限では新しい操作を拒否する。受領証と再送の記録はサーバーの存続期間に限られ、再起動をまたぐ再送は保証しない。

## 完了イベント

stdio の MCP は `notifications/xirius/operation` を送る。通常の編集も、応答後に終わる書き出しも同じ窓口。`params.receipt` が操作を示し、`params.result` が確定した結果を示す。
`ops.receipt` に ID を渡して現在の状態を取得することもできる。

HTTP は起動時に返す `events_url` の SSE でもイベントを送る。MCP と同じ Bearer トークンと localhost の制限が掛かる。SSE の event 名は `operation`。接続時は data に `hello`、遅れた受信者には `resync: true` を送り、サーバー終了時にはストリームを閉じる。`resync` の後は受領証から状態を取り直す。

承認待ちの操作は実行せず、ユーザーが管理用の窓口で回答すると元の受領証を完了する。`ai.permission.set` の AI からの要求も毎回承認を待つ。AI の権限がオフの場合は、受領証と結果ページの取得も拒否する。

## 差分と大きい結果

編集結果の `changes.counts` は対象ごとの追加・削除・変更数。`data.state_hash.before` と `after` は曲の内容の指紋で、暗号学的なハッシュではない。プレビューでは曲の内容を変えない。
長い処理の完了結果にも、元のコマンド名とハッシュが付く。

大きい結果は `summary`・`result_id`・`pages` を返す。成功・失敗・承認待ちの旗と承認トークンは要約でも残す。
MCP の `ops_get-result` に `id` と 0 始まりの `page` を渡し、各ページの `text` を順に連結して JSON として読む。ページは Unicode の文字数で 4,096 文字ずつ分ける。
結果の保存上限は 256 件または合計 64 MiB。古い結果のページは削除され、取得時に `not_found` を返す。

## 別プロセス

`xirius --command-host` は Session と engine の窓口を独立したプロセスで動かす。標準入出力のパイプで `Hello`・`Request`・`Response` の JSONL を送り、最初の照合が済むまでコマンドを受けない。
`xirius_mcp::ipc::PipeHost` は同じ `Host` の実装なので、同じプロセスと別プロセスに同じ試験を通せる。単独のホストは音声装置を開かず、書き出しはオフラインで描画する。

## 同じ曲を同時に開いたとき

画面で開いている曲を、`xirius --song <dir> …` や MCP のサーバーが同時に開いて書くことがある。命令は走っている画面へは送らず、各プロセスが曲のフォルダーを直に開く。

- 履歴・版・録音（PRJ-023）: プロセスごとに別のレーンで履歴を持つので、互いの段・版・録音を消さない。録音の片付け（`project.cleanup`）は、ほかのプロセスが開いている間は `conflict` で断る（`dry` で数えるだけなら通す）。
- `project.json` は最後に保存したプロセスの中身になる。CLI は 1 コマンドごとに曲を開き、実行して保存する。どこから始めるかは次のとおり。
  - 画面が開いている間の最初のコマンドは、画面の今の曲（保存していない編集を含む）から始める。
  - 次からは、前のコマンドの続きから始める。その間にほかのプロセス（画面）が `project.json` を保存していたら、そのファイルを 1 段として取り込んでから始める。前のコマンドの段は、その下に残る。
- MCP のサーバーは曲を開いたまま持つ。各コマンドの前に、CLI が開くときと同じ決まりで `project.json` を見る（PRJ-024）。
  - 保存していない段が無く、そのセッションが最後に読み書きした後にほかのプロセスが `project.json` を保存していたら、そのファイルを 1 段（`project.reload`、画面の呼び名は「ほかのアプリの変更」）として取り込んでから実行する。読むだけのコマンドも、取り込んだ後の曲を答える。
  - 取り込んだ回の結果の `events` には `{"event": "project.reload", "step": 段の番号, "message": …, "changes": …}` が入り、HTTP の SSE にも同じ名前で流れる。
  - 自分の保存の後は取り込まない（段も増えない）。保存していない段があるとき（保存の許可が無い AI の編集）は取り込まず、そのセッションの曲のまま続ける。
  - 見るときは、先に `project.json` の大きさと更新時刻を読み、前に同じファイルと確かめた時のままならファイルを読まない（PRJ-025）。変わっていたら中身のハッシュを比べるので、時刻だけ変わった同じ中身は取り込まない。書かれてから 2 秒たつ前の大きさと時刻は覚えないので、同じ大きさ・同じ時刻で書き換えた保存も取り込む。
- 画面が保存した後に打つ最初の `history.undo` は、CLI でも MCP でも、自分の最後のコマンドではなく、取り込んだ画面の保存を戻す。CLI・MCP のレーンでは、画面の保存も 1 段だから。もう一度 `history.undo` を打つと自分の段を戻す。戻した結果は `project.json` に書かれ（MCP の AI は保存の許可があるとき）、画面に保存していない変更が無ければ、画面はそれを「ほかのアプリの変更」として読み込み、札の「元に戻す」で戻せる。
- 画面はフォルダーの `project.json` を見張り、ほかのプロセスの保存を読み込む（UI-289）。中身が画面の最後に書いたものと同じなら画面自身の保存として扱い、何もしない。続けて書かれたら、最後の書き込みから 300 ms 後に 1 回だけ扱う。
  - 画面に保存していない変更が無いとき: すぐ読み込み、履歴に 1 段「ほかのアプリの変更」（`project.reload`）を足す。元に戻す（Ctrl+Z）で前の曲に戻る。
  - 保存していない変更があるとき: 読み込むかを聞く。読み込むと、画面の変更はその段の下に残り、元に戻すで戻せる。× で断ると画面の曲のまま。ほかのプロセスがもう一度保存したら、また聞く。
  - 曲を開き直さないので、再生は続き、プラグインの準備のカードも出さない。プラグインは元に戻すと同じ道で入れ替える。
  - ドラッグ・録音・名前の入力・保存の間は待ち、終わってから扱う。
- 読み込みを元に戻しても、`project.json` はほかのプロセスが書いた中身のまま。次の CLI のコマンドはその中身から始めるので、戻した変更は CLI の次の保存で戻ってくる。画面の曲を残すなら、画面で保存して `project.json` を画面の曲にしてから CLI を使う。
- MCP で AI に保存の許可が無いときは `project.json` が変わらないので、画面には何も起きない。
- AI の保存（AI-018）は、`project.json` がそのセッションで最後に読み書きしたファイルのままのときだけ上書きする。上の取り込みの後は、取り込んだファイルと比べる。保存していない段があって取り込まなかった間に画面が保存していたら上書きを断るので、画面の保存は消えない。
